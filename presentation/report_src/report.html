1Executive summary

Cadence, a global financial services firm, wants its employees to use an AI agent to analyse business documents. Its policy, however, forbids personal data (PII) from being processed by AI models. We built the PII Sanitization Gateway: a local application that sits in front of the AI, removes the personal data from a document, proves that it is gone, and only then lets the document through.

The solution in one paragraph

The Gateway accepts PDF, DOCX and PPTX files, including scanned PDFs and screenshots inside documents, which it reads with OCR. It extracts every piece of text while remembering exactly where each piece came from (page, slide, table cell, file property). It detects PII with 35 rule-and-checksum recognizers plus context-aware name detection, and replaces each value with a typed, consistent placeholder such as [PERSON_1]. It then re-scans the result with a second, independent checker. Only if that check is clean is the document marked SAFE and released to downloads or AI analysis. If anything is uncertain (the file can't be read, OCR is missing, PII remains, a component crashes), the document is BLOCKED and nothing is released. This "fail closed" behaviour is the core security property.

What makes it trustworthy

  • Local by default. Extraction, OCR, detection and the default analysis all run on the user's machine. Raw documents never leave it.
  • Defence in depth. Detector → independent safety net → remediation loop → release gate → egress guard before the AI → re-verification of redacted files.
  • Explainable. Every finding shows its type, masked value, exact source location, confidence and the method that found it.
  • Meaning is kept. [PERSON_3] approved the exception raised by [PERSON_7] is still useful to an AI, without identities.
  • Honest about limits. SAFE means "two independent scans found no PII", not a mathematical proof. Known gaps are listed (chapter 15).

Deliverables: the working application, CLI, test suite and evaluation harness, nine sample test cases, the interview deck with speaker notes, the website guide and this report (chapter 18).

2The actual problem

2.1 The business scenario

Cadence is a global financial services firm. Employees use an AI document-analysis agent to summarise and question business documents: risk policies, organisational packs, training guides and process documents. These documents routinely contain personal information: employee names, e-mail addresses, phone numbers, staff IDs, and sometimes government IDs, bank details, dates of birth and home addresses. Company policy prohibits PII from being processed by AI models.

The central questionHow can Cadence extract useful information from business documents with AI without exposing sensitive personal information to the AI model?

2.2 Why simply "banning the AI" or "being careful" does not work

  • Banning the tool removes the productivity gain and pushes people towards unsanctioned tools, which is a bigger risk.
  • Asking people to remove PII by hand is slow, inconsistent and error-prone, especially in an 85-page training document or a 35-page scanned policy.
  • A policy written on paper does not stop a document from being pasted into an AI. A technical control in front of the AI enforces the policy automatically.

2.3 Why this is technically hard

DifficultyWhy it matters
Many formatsPDF, Word and PowerPoint store text in completely different structures: pages, paragraphs, tables, text boxes, shapes, speaker notes, comments, file properties.
Scanned documentsA scanned PDF has no text at all, only images. Without OCR, a tool would "see nothing" and could wrongly call the document clean.
PII hidden in odd placesNames in screenshots, in file "author" properties, in speaker notes, in tiny figure text, or split across table columns.
Names have no fixed formatE-mails and phone numbers follow patterns. Names don't, and the same person appears as "Naomi K. Osadebe", "N. Osadebe" and "Osadebe".
OCR noiseOCR damages text: "@" disappears, spaces appear inside e-mails, a phone number gets split across two columns.
False positivesPolicy IDs (GRP-POL-001), case numbers, dates and version numbers look like PII but are not. Over-redaction destroys the document's usefulness.
False negativesA single missed value is a leak. The system must be designed so that misses are caught or the document is blocked.
Keeping meaningReplacing everything with "[REDACTED]" makes analysis useless. The AI still needs to know who approved what, and where.
ExplainabilitySecurity teams must be able to see what was removed, where, and why, without the audit log itself leaking PII.

2.4 Consequences of failure (potential risks, not confirmed incidents)

  • Privacy violations and exposure of employee or customer data to a third-party AI service.
  • Regulatory and compliance risk (financial-sector privacy obligations).
  • Loss of trust in AI-assisted work inside the organisation.

Note: the Cadence sample pack itself asks that its contents not be uploaded to generative-AI tools. That is the exact situation this Gateway makes safe.

5.3 Design principles behind the architecture

  • One common document model. Every extractor outputs the same structure, so detection and redaction are format-independent.
  • Separation of concerns. The UI only displays results. All security logic lives in the pipeline, so the CLI, tests and UI share exactly the same checks.
  • Interfaces between modules. Extractor, detector, redactor and verifier are defined as protocols (interfaces/), so any one can be replaced without touching the others. For example, the evaluation harness can plug in a baseline detector.
  • Never raise, always explain. Extraction failures become warnings and BLOCKED reasons, never crashes and never silent passes.

5.4 Core data structures

6Phase-by-phase processing

This chapter follows one document through the system and names the exact library used in each phase, and why.

6.1 Phase 0: Upload and session handling

  • Streamlit file_uploader accepts one or more PDF/DOCX/PPTX files (up to 200 MB each).
  • The file bytes are hashed with SHA-256 (Python hashlib). The first 16 hex characters identify the document, so re-uploading the same content does not re-process it.
  • The document and its result are kept in Streamlit session state (in memory, for this browser session only). Nothing is written to a database. Switching views never re-runs the pipeline.
  • For processing, the bytes are written to a temporary file (tempfile) that is deleted immediately afterwards.

6.2 Phase 1: Extraction (extraction/)

FormatLibraryWhat is extracted and how
PDFPyMuPDF (pymupdf 1.28)Native text layer with positions. Pages with no text layer are rendered to images and sent to OCR. Low-confidence or small-text regions (figures, screenshots) are found and re-read at 600 dpi. Document properties are read too.
DOCXpython-docx 1.2 (+ lxml)Body paragraphs, tables (row/column kept), headers/footers, text boxes, footnotes, endnotes, comments, file properties, and embedded screenshots (sent to OCR).
PPTXpython-pptx 1.0Every shape including groups and tables, speaker notes, pictures (OCR), file properties.
Images / scansTesseract 5.5 via pytesseract 0.3; Pillow 12Pillow converts to greyscale and auto-contrasts, then Tesseract OCR returns paragraphs with word boxes and confidence. Pages are OCR'd in parallel (a ThreadPoolExecutor drives separate Tesseract processes, up to 8; OMP_THREAD_LIMIT=1 prevents CPU oversubscription).
EMF/WMFLibreOffice (optional)Vector pictures inside Office files are converted to raster for OCR when LibreOffice is installed. Otherwise they are listed in warnings for manual review.

Output: a NormalizedDocument of ordered blocks, each with its source. Never raises: a corrupt or unsupported file produces an ERROR warning, which later makes the gate block the document.

6.3 Phase 2: Detection (detection/)

  • Structured recognizers (Python re plus hand-written validators): 35 patterns for e-mail, phone, SSN, PAN, Aadhaar, passport, card, IBAN, bank account, DOB, address, IP, employee ID and more (detail in §7).
  • Person names with spaCy 3.8 and the en_core_web_sm model for named-entity recognition, combined with rule-based evidence (context cues, e-mail corroboration, table headers, a given-name lexicon) and document-wide propagation.
  • Output: a list of PIIFindings with type, value, location, confidence, method and an entity_key linking spellings of the same person.

6.4 Phase 3: Redaction (redaction/redactor.py, pure Python)

  • Works on a deep copy of the document and replaces exact character spans right to left, so offsets stay valid.
  • A finding is redacted if it is validated (checksum or label) or its confidence is ≥ 0.5. Lower-confidence candidates are not dropped silently: they are listed as needs review.
  • Overlapping findings are merged and the longest one names the tag. Placeholders are numbered in document order.

6.5 Phase 4: Verification and gate (verifier.py, gate.py)

  • The sanitized copy is scanned again by the same detector and by an independent regex safety net.
  • Anything found is redacted and the document is scanned again (at most 2 scans in total). If PII is still present, the result is BLOCKED (residual_pii).
  • Before verification, extraction problems are checked: errors, unread scanned pages and empty content all block the document.

6.6 Phase 5: Release and outputs (output.py, file_writer.py)

  • Sanitized text (SAFE only): every block with its source label.
  • JSON audit report (always): status, reason, counts, masked values (Ra********ma) and per-run keyed hashes. No raw PII.
  • Redacted original-format file (optional, SAFE only):
    • PDF: PyMuPDF redaction annotations are placed on the OCR word boxes, then apply_redactions destroys the underlying pixels and text. Figures that contained PII are removed, metadata is rewritten, and the result is re-OCR'd at 400 dpi until clean.
    • DOCX/PPTX: the file is opened as a ZIP (zipfile) and every XML part is rewritten with lxml: body, tables, headers, footers, text boxes, notes, comments, properties, hyperlinks. Screenshots that contained PII are replaced with a neutral image (Pillow).
    • The written file is verified. If it cannot be verified, it is not kept.

6.7 Phase 6: AI analysis (ai_layer/)

  • Only SAFE results are accepted. Anything else raises AnalysisBlocked.
  • Egress guard: right before sending, the outgoing text is scanned once more with the safety net. Any hit cancels the call.
  • Local provider (default): an offline brief built in Python: summary, headings, "must/shall" obligations, key terms, PII counts, and passage retrieval for a question.
  • Claude provider (optional): only if ANTHROPIC_API_KEY is set. It calls the Anthropic Messages API with Python's standard urllib, sending sanitized text only, with a system prompt telling the model never to re-identify anyone.

6.8 Phase 7: Presentation (app/)

  • Streamlit 1.65 renders the app. pandas 3.0 builds the findings tables. Custom HTML/CSS/JavaScript (in ui.py) provides the design, animations and light/dark theming.
  • While a document is processed, a live status panel reports each stage only after it has actually finished, using a progress callback added to pipeline.process().

6.9 Phase 8: Quality assurance

  • pytest 9 runs 247 unit and end-to-end tests on fake documents generated on the fly.
  • The evaluation harness measures recall, precision, residual PII, traceability and structure retention against labelled ground truth, and flags regressions.

7PII detection in depth

7.1 Structured recognizers (35 rules)

TypeRule (precision comes from validation or labels)
EMAILStandard addresses plus OCR-damaged forms (space around "@", lost "@" with a known domain, truncated domain).
PHONEInternational +CC, North-American, labelled ("Tel:", "Mobile"), and fragments split across table columns by OCR (never swallowing a neighbouring date).
SSNddd-dd-dddd with US Social Security validity rules; labelled variants; "SSN ending 4821".
PAN · AADHAAR · NATIONAL_ID · PASSPORTIndian PAN (entity-type letter check), Aadhaar (Verhoeff checksum), UK NINO, PESEL/TIN when labelled, passport when labelled.
CREDIT_CARD · IBAN · BANK_ACCOUNTCards with the Luhn checksum; IBAN with mod-97; labelled account numbers; "card ending 4421".
DOBOnly when labelled ("DOB", "date of birth", "born"). Ordinary business dates are never PII.
ADDRESSStreet number + name + suffix (+ unit, city, state, ZIP); "City, ST 12345"; UK postcode; labelled Indian PIN.
IP_ADDRESSIPv4 with valid octets (section numbers like 1.2.3.4 are excluded).
EMPLOYEE_IDEMP-41077, contractor and director prefixes (MER-IN-4471, DIR-0058, CTR-, STF-), labelled staff/badge IDs, OCR splits.

Deliberately not matched: business identifiers such as GRP-POL-001, ISS-2026-0112, RSK-4488, CTL-IAM-04. These are pinned by tests, so a future change cannot start redacting them.

  • Cleaning: OCR'd tables glue neighbouring cells onto names. These are trimmed, e.g. "High Yusuf O. Balogun" becomes "Yusuf O. Balogun".
  • Rejection: business vocabulary ("Risk Owner", "Trigger Type"), all-caps role lines, names followed by a company suffix ("… Ltd"), and words the same document also uses in lower case.
  • Propagation: once a person is confirmed, every form is found everywhere: full name, initials, "Surname, First", upper case, a distinctive bare surname, and OCR variants one letter away. All share one entity_key, and therefore one placeholder.
  • Safety rule: NER alone never creates a name from screenshot OCR, which is too noisy. Other evidence still applies there.

7.3 Why a hybrid approach (rules + NER + context)

Regular expressions are precise and explainable for values with a fixed shape, especially when backed by checksums, but they cannot find names. A statistical NER model finds names but makes mistakes and gives no checksum-like guarantee. Document-level evidence (the same person's e-mail on another slide, a "Name" column header) is what makes name detection reliable on real business documents. Combining all three, and then verifying independently, gives both high recall and explainability.

8Redaction, verification and the release gate

8.1 Typed, consistent placeholders

Jane Smith emailed John Doe becomes [PERSON_1] emailed [PERSON_2]. The same value, or the same person under a different spelling, always gets the same tag across the whole document. An AI can still reason about relationships ("who approved what") without learning who anyone is. A generic "[REDACTED]" would destroy that meaning.

8.2 The gate decision

StatusReasonWhen it happens
SAFEverified_cleanThe first re-scan found nothing.
SAFEverified_after_remediationResiduals were found, redacted, and the next scan was clean.
BLOCKEDextraction_failedThe file could not be opened or parsed (corrupt, protected, wrong type).
BLOCKEDincomplete_extractionPart of the content was never read (e.g. a scanned page while OCR is missing).
BLOCKEDno_contentNothing was extracted, so nothing could be verified.
BLOCKEDresidual_piiPII was still present after the last allowed pass.
BLOCKEDverification_errorThe detector crashed. Only the exception type is recorded.
Why "fail closed"?A blocked document costs a few minutes of manual review. A leaked document cannot be un-sent. When the system cannot prove a document is clean, it treats it as unsafe, so "nothing was read" is never mistaken for "nothing was found".

8.3 The independent safety net

The safety net (redaction/verifier.py) is a separate, conservative set of checks: e-mail, phone, SSN, card (Luhn), IBAN (mod-97), PAN, passport after the word "passport", labelled DOB, street addresses and IPv4. Because it is implemented separately from the main detector, a bug or blind spot in one is unlikely to be repeated in the other. It is used in verification, at AI egress and when verifying written redacted files.

8.4 Audit without a second copy of the PII

Reports and logs record what happened (type, count, location, method, confidence, gate status and reason) and identify values only by masked forms and keyed hashes. The hash key is random per run, so short values such as phone numbers cannot be reversed with a lookup table.

9Security and privacy design

9.1 Threats and controls

ThreatControl in this project
Raw PII sent to an AI modelRelease gate; AI layer accepts SAFE only; egress guard re-scans the outgoing text.
Scanned page silently skippedMissing OCR or OCR failure → incomplete_extraction → BLOCKED.
Detector misses a valueIndependent safety net; remediation loop; BLOCKED if anything remains.
Component crash leads to a partial resultAny exception in verification → verification_error → BLOCKED.
Redacted PDF still contains hidden text or pixelsTrue redaction (apply_redactions destroys pixels and text), figure removal, 400 dpi OCR re-check.
Audit log becomes a PII storeMasked values and per-run keyed hashes only.
Malicious content in a document rendered in the UIAll document-derived text is HTML-escaped before display.
Accidental display of raw PII on screenOriginal text is hidden in Compare unless the user enables it in settings; masked values everywhere else.
Data persisted on disk or in a databaseNo database. Session-only memory; temporary files are deleted after processing.
Third-party services seeing the documentAll processing is local; no cloud OCR/NER; no web fonts or CDNs in the UI.

9.2 Security principles

  • Local by default: the only possible outbound call is the optional Claude analysis, and it carries sanitized text of SAFE documents only.
  • Fail closed: uncertainty is treated as unsafe.
  • Defence in depth: several independent controls, so one failure is not a leak.
  • Least data: keep only what is needed, for as long as needed (the browser session).
  • Explainability: every decision can be traced and justified.

9.3 What "SAFE" does and does not mean

SAFE means that two independent scans found no PII within the detection scope. It is not a mathematical guarantee. Content the system cannot read (handwriting, vector pictures without LibreOffice) is reported in warnings for manual review, and OCR quality limits recall on heavily degraded scans. This is why the system is designed as one layer in a governance process, with human review for uncertain cases.

11Why this stack and not the alternatives

The single most important constraint is the problem itself: we may not send raw personal data to a third party. Any tool that needs the raw document to leave the machine before redaction is ruled out, however good it is. The second constraint is explainability and testability: a security team must understand and reproduce every decision.

11.1 OCR

OptionWhy not chosen (or chosen)
Tesseract (chosen)Free, local, mature, good on typed business documents, gives word boxes for true PDF redaction.
AWS Textract, Google Vision, Azure Document IntelligenceExcellent accuracy, but the raw scanned page with all its PII would be uploaded to a cloud service before any redaction, which defeats the purpose. They also add cost and an internet dependency.
EasyOCR, PaddleOCRDeep-learning OCR needs PyTorch/Paddle (large installs, GPU for good speed); on a CPU laptop it is slower for 35-page scans and harder to install for a demo.

11.2 PII / name detection

OptionWhy not chosen (or chosen)
Rules + checksums + spaCy + document evidence (chosen)Local, fast, deterministic, explainable per finding; tuned for OCR noise, tables and document-wide name propagation.
Microsoft PresidioA good open-source framework built on the same idea (regex + spaCy). We needed document-level logic that Presidio does not do out of the box (cross-slide e-mail corroboration, table-header evidence, one placeholder per person across spellings, OCR-split phone fragments), plus tight integration with source locations. A custom detector gave that control without an extra framework.
Transformer NER (BERT, RoBERTa)Often more accurate on names, but needs much larger models, slower CPU inference or a GPU, and is harder to explain. A good future upgrade behind the same interface (§16).
Using an LLM to find PIISending the raw text to a hosted LLM to find PII would itself break the policy. A local LLM would be heavy, slow and non-deterministic, which is hard to test and audit.
Cloud DLP (Google Cloud DLP, AWS Macie/Comprehend, Azure Purview)Strong products, but they need the raw data in the cloud, add cost and vendor lock-in, and are not available offline. In an enterprise they could complement this tool as a second opinion.
Regex onlyCannot find names and produces false positives on numbers without context.

11.3 Document parsing

OptionWhy not chosen (or chosen)
PyMuPDF (chosen)Fast, gives text positions, renders pages for OCR, and is one of the few Python libraries that performs true redaction (removing underlying text and pixels).
pdfplumber / pdfminer.six / PyPDF2Good for text and tables, but no page rendering for OCR and no true redaction, so a second library would still be needed.
python-docx / python-pptx + lxml (chosen)Keep native structure (tables, shapes, notes, properties) for traceability; lxml covers parts the libraries don't expose.
Convert Office → PDF first (LibreOffice)Loses structure (which slide, shape, table cell, speaker note, property), hurting traceability; heavy dependency; only used optionally for EMF/WMF pictures.
Apache TikaBroad format support but needs a Java server and returns flattened text without precise locations.

11.4 Application and interface

OptionWhy not chosen (or chosen)
Streamlit (chosen)Full interactive web app in pure Python (uploads, tables, downloads, session state), quick to build and easy to demo locally; the brief explicitly allowed a "simple custom interface".
Google ColabAllowed by the brief, but documents would be uploaded to Google's cloud runtime. That is not acceptable for real PII, and it is not a usable tool for analysts.
Jupyter NotebookGood for exploration, but not an application a business user can operate; harder to enforce the release flow.
React/Angular + FastAPI/Flask/DjangoA production-grade option, but two codebases, an API layer and much more time for a case study. The pipeline is already separated from the UI, so this migration is possible later (§16).
GradioSimilar to Streamlit, aimed at model demos, with less control over multi-view workspace layouts.
Desktop app (PyQt, Electron)Packaging and distribution overhead; a browser UI on localhost gives the same "local only" property more simply.

11.5 Other choices

  • No database: storing documents or results would create a new store of PII. Session memory is enough for the use case.
  • No Anthropic SDK: the AI layer is optional and small; the standard library avoids another dependency.
  • Python rather than Java/Node: spaCy, PyMuPDF, python-docx/pptx and pytesseract have no equally mature equivalents in a single other ecosystem.
  • Single-script navigation rather than Streamlit multipage: Streamlit's file uploader cannot keep files across pages, so one script with a sidebar view selector and a session document store keeps uploads and results while switching views.

12The application (user interface)

The app runs at http://localhost:8501. A left sidebar holds the navigation, the active-document picker and a collapsible System & settings panel. The main area shows the selected view.

12.1 Sidebar

  • Brand: "PII Gateway — Secure document processing".
  • Navigation: Workspace · Findings · Sanitized Text · Compare · AI Analysis · Reports & Downloads, with an orange active marker. It is keyboard-accessible (Tab, then arrow keys).
  • Active document: appears after upload; chooses which processed document the detail views show.
  • System & settings: OCR, name model, recognizers and AI-provider status, plus two options: "Create redacted PDF/DOCX/PPTX during processing" and "Show original text in Compare" (off by default for privacy).

  • Identity: navy, off-white and Optiv-style orange; glass cards; colour-coded placeholder tags by type.

13Testing and evaluation

13.1 Automated tests (run on 14 October 2026)

Result: 247 passed, 3 skipped. All tests use fake data generated on the fly. Coverage includes:

  • Extraction: scanned PDF uses OCR; DOCX screenshot is OCR'd; corrupt and unsupported files don't crash.
  • Detection: hard negatives (policy and case IDs, dates, versions), overlaps keep the longest span, phone fragments split across table cells, names glued to table columns are trimmed, table headers mark names.
  • Redaction: same value gets the same placeholder across blocks, multiple findings keep offsets valid, overlaps merge, source metadata is preserved, values split by line breaks.
  • Gate: residual PII blocks; failed extraction, empty documents and scanned pages without OCR block; a detector crash fails closed.
  • AI layer: a blocked document never reaches it; the egress guard catches leaks.
  • File writer: a scanned PDF copy is verified by OCR; blocked documents are not written.

13.4 Metric definitions

  • Precision = correct PII detections ÷ all detections.
  • Recall = correct PII detections ÷ all actual PII in the labelled set (every occurrence counts).
  • Structure retention = pages, slides and tables represented, plus non-PII words kept, compared with an independent reference extraction.
  • Residual PII = an independent text search of the sanitized output for every labelled value.

15Limitations and known gaps

15.1 Known gaps found by our own tests

CaseWhat leaksWhyPossible fix
TC06A bare first name ("Rafael") after the full name was detectedPropagation covers distinctive surnames and some first names, but not this onePropagate the capitalised first name of every confirmed person when it is not a common word.
TC09"AnitaPatel" (OCR merged two words in a screenshot)CamelCase OCR tokens are not split before name matchingSplit merged CamelCase tokens; treat user lists in screenshots as PII by default.

15.2 General limitations

  • OCR quality bounds recall on degraded scans; handwriting and vector images (EMF without LibreOffice, SVG) are flagged for manual review rather than read.
  • Ambiguous names that are also ordinary words can be missed or over-redacted.
  • Identifier formats outside the US/UK/EU/Indian formats in the test material need new patterns.
  • English only: the NER model and lexicon are English.
  • Over-redaction of business contact data is a deliberate security-first trade-off.
  • Evaluation: the gold labels need a human spot-check; the Cadence files are not in this repository copy.
  • Deployment: a single-user local app; no authentication, multi-user queue or central audit store yet.
  • UI: the scroll-linked effects need a modern Chromium/Safari browser (others get simpler fades). The hero artwork overflows by about 5 px at very narrow phone widths.

AGlossary

TermMeaning
PIIPersonally identifiable information: data that identifies a person directly (name, e-mail, ID number) or indirectly when combined with other data.
OCROptical character recognition: turning an image of text into machine-readable text (Tesseract here).
NERNamed-entity recognition: a language model that labels spans such as PERSON (spaCy here).
Placeholder / tagA typed token such as [PERSON_1] that consistently replaces a value.
ChecksumA mathematical validity check (Luhn for cards, Verhoeff for Aadhaar, mod-97 for IBAN) that rules out random numbers.
Safety netThe independent regex scanner used in verification, at AI egress and for written files.
GateThe decision step that marks a document SAFE or BLOCKED.
Egress guardA final scan of outgoing text immediately before an AI call.
Fail closedWhen in doubt, block; never release unverified content.
Recall / PrecisionShare of real PII found / share of detections that are real PII.
Content blockOne unit of extracted text together with its source location.

BAnticipated questions and answers

QuestionAnswer
Why not regular expressions alone?Names have no fixed format and many numbers look like PII without being PII. Regex with checksums handles structured IDs; NER plus document evidence handles names.
How do you stop PII reaching the LLM?Redact → independent re-scan → remediate → gate → egress guard. Only SAFE text is ever released; failed or partial extraction blocks.
What happens when OCR or extraction fails?The document is BLOCKED with a reason. "Nothing read" is never treated as "nothing found".
How do you limit false positives?Checksums, "only when labelled" rules, business-vocabulary filters and negative tests for policy and case IDs.
How do you measure structure retention?Pages, slides, tables and non-PII words compared with an independent reference extraction; measured 99.8–100 % vs. the 80 % target.
Is 99.5 % recall enough?Recall alone is not the guarantee; the independent re-scan and the gate are. Measured residual PII in released output was zero.
Why not use an LLM to detect PII?Sending raw text to a hosted LLM would itself break the policy; a local LLM is heavy, slow and non-deterministic, which is hard to audit.
How is auditability achieved without storing PII?Reports log type, location, method, confidence and gate reason, with masked values and per-run keyed hashes only.
How would you scale it?Stateless service behind a queue, scaled OCR workers, deployed as a mandatory proxy in front of the AI agent.
What are the main limitations?OCR quality, ambiguous names, untested locales, English-only NER, deliberate over-redaction, and gold labels pending human review.
